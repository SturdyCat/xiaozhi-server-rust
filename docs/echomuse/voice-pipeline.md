# EchoMuse 语音管线（voice-pipeline）

> 整理自上游 [wilbowes/EchoMuse docs/voice-pipeline.md](https://raw.githubusercontent.com/wilbowes/EchoMuse/main/docs/voice-pipeline.md)（快照 2026-10，main 分支）；以英文原文与源码为准，本文仅供本仓库开发参考。

从你说出「Hey Rhasspy，关灯」到灯真正熄灭之间到底发生了什么——本文按阶段逐一拆解，用平实的语言说明每个设计选择的收益与代价。

一句话版本：Echo Dot 尽可能干净地拾音并监听自己的唤醒词；听到唤醒词之后，你说的话被送往 controller 与 Home Assistant，由它们判断你何时说完、说的是什么意思。一切可调项都在 dashboard 上设置，无需触碰硬件。

## 管线总览

```
 你的语音
    │
    ▼
┌─ Echo Dot 上 ───────────────────────────────────────────────┐
│  7 麦克风 → 增益 → 回声消除 → 选麦 → 唤醒词                  │
└──────────────────────────────│──────────────────────────────┘
                               │  唤醒词之后你说的话（WiFi）
                               ▼
┌─ controller 上 ─────────────────────────────────────────────┐
│  会话管理（以及唤醒词检测，如果你选择）                       │
└──────────────────────────────│──────────────────────────────┘
                               │
                               ▼
┌─ Home Assistant 内 ─────────────────────────────────────────┐
│  speech-to-text → 意图理解 → 执行 → text-to-speech           │
└──────────────────────────────│──────────────────────────────┘
                               │  语音回复
                               ▼
                      回到 Dot 的扬声器
```

## Stage 1 — 七麦克风

Dot 有 6 个麦克风排成环形、1 个位于中心，全部同时采集，每秒 16,000 次，24-bit 高精度音频。

**收益：**同时听到来自各个方向的声音，并拥有判断你说话*方向*的原始素材。

**局限：**它们只是小圆盒里的微型麦克风，就摆在你的房间里——电视、洗碗机、乃至 Dot 自己的扬声器，它听这些和你说话一样清楚。管线其余的大部分阶段，就是为了对付这一点而存在的。

## Stage 2 — 增益提升（mic gain）

原始采集音量*极低*——实测正常说话只占用了可用信号幅度的一小部分，而旧的处理链路在把音频转换成传输格式时会直接丢掉最安静（信息最丰富）的部分。解决办法：在转换*之前*，把全精度 24-bit 信号放大 24dB（约 16 倍），保住那些否则会永远丢失的细节。

**收益：**仅这一项改动，就让真实房间测试中的语音识别从「三次请求失败一次」变成「可靠」。它是下游一切站立其上的地基。

**局限：**固定增益意味着非常响的事件（贴着设备大喊）可能顶到上限、短暂失真。设备会在日志里统计这些「削波（clipped）」时刻；实践中即使把电视放到电影音量，削波次数也是零。

## Stage 3 — 回声消除（AEC）

Dot 在说话时，它的麦克风会很大声地听到它自己的声音。AEC 保留一份扬声器正在播放内容的精确副本，用数学方法把它从麦克风听到的声音中减掉，剩下的只有*其他*声音——比如你想插话的声音。

**收益：**追问（follow-up）能正常工作（设备能在自己回复的余音之上听到你），而且它自己的语音不会触发或干扰监听逻辑。这也是 **barge-in**（用唤醒词打断助手的话）得以实现的前提（见上游 configuration guide 的 Barge-in 设置）。

**局限：**它只消除 *Dot 自己*的声音——对电视无能为力（那是另一个问题，见 Stage 8）。AEC 默认开启。（自 v2.7.8 起，消除器在两次回复之间保持「热身」状态，而不是每次重新学习——如果以前 barge-in 需要提高嗓门，现在应该不必了。）

## Stage 4 — 麦克风选择（beamforming + lock-back）

空闲监听时，设备总是用中心麦克风——它对各方向一视同仁，所以无论你站在哪里，唤醒词都有效。当你*真的*唤醒它之后，设备切换到朝向你的环形麦克风——对你的拾音略好，对房间其余部分略差。

微妙之处在于*它怎么选*：等 controller 认出唤醒词时已经过去半秒，你说唤醒词的声音早已消散。所以设备持续维护一份两秒的「各方向声能」记忆，唤醒到来时它向*回*查找这段记忆，找到唤醒词真正传来的方向——而不是此刻声音来自的方向。它还按*突变*而非原始响度为方向打分，因此人声能胜过一直响着的电视。

**收益：**指向你的麦克风带来更好的 speech-to-text，LED 方向指示也真的指向你。

**局限：**单支选定麦克风是温和的改进，不是魔法变焦镜头。而且两次对话的间隙里，设备自己的语音可能还残留在那两秒记忆中——在 barge-in/AEC 工作成熟之前，追问型对话只能得到这个特性的弱化版。

## Stage 5 — 持续音频流（仅 controller 模式）

对一台设置为在 **controller 上**检测唤醒词的 Echo，处理后的音频每 32 毫秒经 WiFi 发往 controller，始终如此。这条流*刻意*没有「听起来像语音才发送」的门控。

**收益：**唤醒词识别器看到的是平滑、无间断的音频，可测量地提升准确率——而且设备侧不存在可能漂移、误判你的房间或随时间退化的逻辑（早期更「聪明」的设计真的发生过这两件事；无聊胜出）。

**这条流只存在于设置为 controller 检测唤醒词的 Echo 上。**默认情况下，Echo 自己运行同一个识别器，听到唤醒词之前什么都不发；听到之后才发送后续内容，直到你停止说话（上游 [listening.md](https://github.com/wilbowes/EchoMuse/blob/main/docs/listening.md)）。本阶段其余内容描述的是 controller 侧模式。这也是为什么给这条流加「像语音才发」的门控比看上去难：识别器的内部缓冲区假设音频连续，把门控的碎片拼接起来会可测量地压低它的得分。

**局限：**每台设备在 WiFi 上恒定约 32KB/s——大约是流式传输*回复*音频所用带宽的六分之一，在任何家庭网络中实际不成问题。隐私方面也要说清楚：这条流只去*你的* controller、*你的*局域网，别处都不去——而监听自己唤醒词的 Echo 根本不发这条流。

## Stage 6 — 唤醒词检测（wake-word spotting）

openwakeword 是一个小型神经网络，给每一刻音频打分：「这有多像唤醒词？」越过灵敏度门槛，对话开始。默认它运行**在 Echo 上**，所以在此之前什么都不需要离开设备；设置为 controller 模式的 Echo，则由 controller 对那条流运行它。同一个模型，同一道门槛。

多设备在线时，*听得最响*的那个 Echo 应答——通常就是你在的房间那台。controller 最多等四分之一秒，确保所有听到唤醒词的 Echo 都被计入；在**仲裁窗口**（arbitration window，默认 700ms，可配置）内检测到同一词的其他设备静默退让。一次说话，一次应答，即使你处在两台设备的听力范围内。只有一台 Echo 时没有等待。controller 2.26.0 之前是「最先听到你的 Echo 应答」；[listening.md](https://github.com/wilbowes/EchoMuse/blob/main/docs/listening.md) 记录了这次改动背后的测量数据。

**收益：**无论哪种模式，都可以在 dashboard 上实时更换唤醒词或调整灵敏度。

**局限：**它是一个概率而非确定——灵敏度滑块是误接受 vs 误拒绝的权衡，要按你的房间来调（near-miss 计数器的存在，正是为了让这种调校有据可依，而不是凭感觉）。

## Stage 7 — 会话（turn）

唤醒时：LED 变绿，设备的选麦锁定朝向你，controller 把你的音频输送给 Home Assistant，由它判断你何时说完（用 HA 自己的语音检测器——另有 controller 侧的兜底：如果误唤醒导致根本没人在说话，会对照该房间实测的背景噪声水平，在 5 秒后悄悄结束本轮）。

**收益：**端点检测（「用户说完了吗？」）交给 HA 维护良好的检测器而非自制逻辑；误唤醒兜底自动适配每个房间——安静的书房和喧闹的客厅，无需任何调校就能得到同样合理的行为。

**在确实有人在说话之前，什么都不会送进 Home Assistant。**controller 用一个小型语音检测器（Silero，随唤醒词包一起分发）检查本轮音频并先行扣住；一旦听到语音，再把扣住的内容按序全部发出，所以 HA 拿到的内容与不加扣留时完全一致，只晚了不到一秒。误唤醒，或唤醒后一片寂静，就什么都不发，本轮在 5 秒兜底处安静结束。存在这个机制是因为 speech-to-text 模型对非语音不会返回空：鸭叫下的背景音乐曾被转写成 "Thank you."，并对一个没人问的问题礼貌作答。按钮（button）与追问（follow-up）轮次在 Dot 本机上用同一个模型——由 controller 随唤醒词文件一起安装。

**还有第二道兜底，用于那个检测器根本没启动的情况。**HA 需要先听到约三分之一秒它有把握的语音，才会判定你开始说话——在它做出这个判定之前，它无法判定你已经停止。像 "stop" 这样的短指令可能永远够不到这个门槛，于是 HA 等满自己 15 秒的上限，然后按「你只是说完了」上报本轮。它的上报里没有任何异常标记，这就是为什么很长时间里，这看起来像 Echo 反应慢。

所以 controller 会盯着这个特定形态——听到了语音、而 HA 迟迟没有表示它注意到了——并在你停止后约一秒由自己结束本轮。只要 HA 自己的检测器在正常工作，仍由它决定；它的判断比我们好。已上游上报为 home-assistant/core#181747。

**局限：**嘈杂的房间里，检测器有时会多挂一拍，电视对白的尾巴会跟着混进 speech-to-text（你偶尔会看到转写末尾多出一截无关短语）。清理送往 speech-to-text 的音频，是计划中的下一个修复。

## Stage 8 — 语音转文本、意图理解、执行

Home Assistant 的 Assist pipeline 接管：你的语音变成文本（Whisper 或你配置的任何 STT），文本变成意图（「关闭 + 厨房的灯」），动作执行，回复生成。

**收益：**全是标准、文档完善的 Home Assistant 机制——HA 支持的每个 STT/LLM/TTS 选项都能用，EchoMuse 无需了解其中任何细节。

**局限：**这里也是大部分*时间*的去处（转写与回复生成是最慢的步骤，在性能普通的硬件上尤其如此），也是背景噪声导致的转写错误最终暴露的地方。更好的麦克风和更干净的音频有帮助，但不能完全替代一个好的 STT 模型。

## Stage 9 — 回复

回复音频经 controller 回传并流式送往 Dot，Dot 对它整形并播放，同时把一份副本送入回声消除器（Stage 3），供麦克风减去它。satellite 向 HA 索要扬声器原生的格式——48kHz 单声道 WAV——音频直接透传，无需解码。以前是 FLAC，解码器内部会积压最多 1.7 秒语音；当 HA 在句子之间停顿（它在等语言模型给出下一句）时，积压的音频晚到，长回答就中途静音。HA 发来的其他格式仍用 ffmpeg 解码。

播放时，环形灯随音频起伏；它在 Dot 报告*确实*播完时熄灭，而不是 controller 估算该播完时。旧的估算在慢 WiFi 上可能提前几秒熄灯——只有设备自己知道它的缓冲区何时见底。

整形按顺序分三级：**equalizer**，然后 **bass guard**，最后 **limiter**——全部来自上游 configuration guide。顺序很重要。guard 砍掉小喇叭实际发不出的低频，这正是中频听起来清晰而非闷箱的原因；把它放在 limiter 之前，limiter 就不必为了照顾没人听得见的低频峰值而压低整个回复。实测 guard 开启时，中频反而*略响*。

整形**在 Dot 上**运行，就在音频到达扬声器的那一刻，所以 dashboard 上改设置，不到一秒就能听到效果，而不是等已缓冲的几秒播完。做不到的固件由 controller 代为整形，与以前完全一样；两端协商由谁来做，音频绝不会被整形两次。

**收益：**每台设备声音一致、经过调校，dashboard 实时生效。代价是占用一些 Dot 的 CPU。

回复**在 HA 仍在生成时就流式发出**：内容到达即送往 Dot，而不是等全部取回。长回答开始出声的时刻与短回答大致相同，不必等最后一个词合成完才听到第一个词。三级整形都跨块保持状态，拼接处没有咔哒声。

默认在 HA 生成完回复后才开始播放。开启 **Speak while the reply is written**（Playback 设置）后，HA 一发出「回复首段文本已到达」的信号（`tts_start_streaming`）就开始播放——模型慢时，这远早于回复完成。只有对话 agent 与 TTS 引擎都支持流式时 HA 才发该信号；不支持时（内置回答，或无法边收文本边合成的 TTS 引擎），无论开关如何，都在回复完成后开始。开启该设置后，controller 等待回复开始的 30 秒，必须由最先的词而不是最后的词来满足。

回复到达扬声器的速度不会快于生成速度，模型或 TTS 引擎比语速慢，就会在句间留出空隙。这就是该设置默认关闭的原因。

**局限：**用语音打断回复（**barge-in**）在启用后可用——对着它说唤醒词，回复即被切断——它默认开启且依赖回声消除（Stage 3，同样默认开启）：播放期间麦克风保持活跃，回声消除防止设备把自己唤醒。重启后的第一次回复就能用：Dot 把回声消除器学到的关于自己扬声器的知识保存下来、开机时重新加载，而不是花最初 10–20 秒的语音重新学习。*只说话不打唤醒词*式的打断，是刻意不去尝试的。

## 语音之外 — 音乐

每台 Echo 在 Home Assistant 里以**媒体播放器**（media player）出现，真的可以往上面播东西：`media_player.play_media`、HA 媒体浏览器、Music Assistant、电台流。controller 用 ffmpeg 解码投给它的任何内容并流式送往扬声器，保持领先几秒缓冲，让 WiFi 抖动不至于变成听得见的空隙。暂停和停止仍然是即时的——它们不等缓冲播完，而是直接丢弃。

音乐播放中说出唤醒词会将其 **duck**（压低）：音乐降为回答之下安静的底噪，回答结束后再升回来。不是暂停。Dot 一听到自己的唤醒词就自行压低，与环形灯点亮同时发生，而不是等 controller 应答。这很重要，原因有二：当你开始说话时，那几秒的提前量已经在 Dot 内部，ducking 必须发生在设备上；而且 Music Assistant 的 flow 流无法 seek，暂停它曾经要付出整段对话时长的代价，有时恢复时已跳到下一首。语音本身从不被压低，被压低的只有它下面的底噪。压低多少由你定（**Ducking**，Playback 区）——这是口味问题，最好在实际房间里用耳朵来定。

音乐中唤醒依赖 AEC 与 barge-in（Stage 3），两者都默认开启：让你能打断助手自己声音的那套回声消除，也正是让它能在歌声之上听到你的原因。

不能混音两路流的旧固件回退到以往行为——对话期间暂停，结束后恢复。

## 设计原则（如果你好奇「为什么会是这样」）

1. **设备能干，controller 聪明。**Dot 只做必须发生在它身上的事：采集、放大、消除自身回声、监听唤醒词、整形要播放的内容。任何可能漂移、误判或需要调校的东西，都放在 controller 上设置——可观察、可更新、不必碰硬件。
2. **测量，而不是改写。**controller 跟踪每个房间的噪声底，并据此做*决策*（有人在说话吗？），但从不改写送往 speech-to-text 的音频。自适应的音频魔改，正是系统历史上最严重 bug 的来源。
3. **无聊而连续胜过聪明而门控。**常开、无处理的唤醒流，取代了一个更聪明但会随时间退化的设计。拿不准时，管线选择可预测的那一个。

## 一次健康的 turn 长什么样

如果觉得 Echo 慢，有用的问题是*哪个阶段*慢——答案每次都指向完全不同的组件。以下数字在下文参考环境上实测，供你对照，而不是凭感觉。

「打开办公室的灯」指令，端到端：

| 阶段 | 含义 | 参考值 |
|---|---|---|
| wake → first frame | Echo 开始推流 | **3ms** |
| speech | 你说话，直到 HA 的 VAD 判定停止 | 3.1s |
| **speech recognition** | Whisper 把音频转成文本 | **1.8s** |
| **intent** | HA 判断你的意图并生成语音 | **0.04s** |
| fetch | 下载语音回复 | 0.4s |
| playback | 播出回复 | 2.2s |
| **total** | 从唤醒词到播完 | **7.1s** |

大头是你说话和助手回答。慢系统膨胀的是 **speech recognition**，这也是对运行机器 CPU 最敏感的阶段：两个共享核心上，同样指令中位数 **4.8s、最高 20.5s**；四个核心为中位数 2.1s、波动 1.6–2.6s。管线其余一切未变。

灯光、定时器这类本地意图在**几十毫秒**内解析。如果你的 *intent* 阶段要几秒而非几毫秒，你多半在走 conversation agent（LLM），而不是 HA 内置意图——这是选择而非故障，但值得知道自己选了哪个。

对比之前须知两件事：

- **重启后的第一个请求一定慢**，因为语音模型按需加载。丢弃它。
- **这些数字是参考，不是指标。**更慢的机器不是坏的。要点是能区分「我的 speech recognition 要 15 秒」和「我的 Echo 没反应」——两者中只有一个是 EchoMuse 的问题。
