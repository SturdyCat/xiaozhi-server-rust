# PRD：NLU 技能概念统一与按控制域分组

- 项目：小智 ESP32 语音服务端
- 作者：许清楚（产品经理）
- 日期：2026-02
- 类型：简单 PRD（系统规划，不含代码实现）
- 铁律约束：ESP 固件协议保持兼容；`end_session` / `other` 为保留训练标签；技能动作中的 MCP 工具名必须是静态字面量；训练标签 = 技能名（改名需重训）。

## 1. 产品目标

将散落在系统中的三类概念——command 命令词表、mcp 工具动作、nlu intents（意图）——在 NLU 层**统一为一个概念：技能（Skill）**，并按**控制目标（控制域：device 设备 / server 服务器 / iot 未来的第三方智能设备）**分组组织。管理台管理员由此获得：一份按域分组、可搜索的统一技能目录；新增技能时只需回答"控制什么目标、执行什么动作"；设备控制类技能（音量、播放控制等）可像提醒类技能一样在管理台编辑并训练；概念减少，心智负担与配置错误显著下降。

## 2. 概念模型（用户视角）——统一术语表

| 统一术语 | 定义 | 映射用户原话 | 覆盖现有概念 |
|---|---|---|---|
| 技能 Skill | NLU 可识别、可执行的最小单元 = 名称 + 例句模板 + 槽位 + 动作 | "现在 nlu 这里统一概念叫做技能" | nlu intents；command 词表条目；原先写死 `mcp:<工具名>` 的动作 |
| 控制域 Domain | 技能的一级分组 = 技能的控制目标类别 | "技能又区分汇总 控制目标与动作，如控制 设备、服务器、iot" | 新增字段，此前无此概念 |
| 动作 Action | 技能执行方式，沿用现有四种：reply / end_session / mcp:<tool> / plan | "每个设备又含有若干技能"中的"动作" | catalog.rs kind，不新增种类 |

**各域归属结论：**

- **设备域 device**：由设备固件 MCP 工具执行的技能。音量加减、静音、播放/暂停/循环、重启、**断开对话（原 command 词表）** 等。command 词表整体并入：退下/闭嘴/关闭 → 即 `end_session` 技能，归设备域（作用于当前会话/设备），词表仅作为其训练样本来源。
- **服务器域 server**：由服务端执行的技能。现有全部 11 个 reminder_* 技能（倒计时/定时/周期/查询/取消，走 plan → tasks.create）、messages.send 离线消息等。即用户所说"计划任务，定时器，倒计时…"。
- **IoT 域 iot**：tuya 等第三方智能设备控制。当前为空白，本次仅做**分组占位与数据模型预留**，不落地任何技能。
- **mcp 工具**：不再是独立概念，降级为设备域技能"动作"里引用的**执行资源**（工具名静态字面量，会话执行时按设备 discovery 声明校验）。

**域划分口径（默认采用，待用户确认）**：按**执行者**分域——设备固件执行的归 device，服务端执行的归 server，第三方云（tuya）执行的归 iot。故音乐播放控制归**设备域**（固件播放器），与用户原话把它归入服务器控制相左，见待确认问题 Q1。

## 3. 用户故事

1. 作为管理员，我想在管理台看到按"设备/服务器/IoT"分组的技能目录并支持搜索，以便快速定位和管理某类技能。
2. 作为管理员，我想新建一个设备域技能（如"调大音量"→ mcp:self.audio_speaker.set_volume），以便用语音控制音箱而不需要理解底层概念。
3. 作为管理员，我想看到 command 词表已被合并为设备域的"断开对话"技能，以便只维护一份入口。
4. 作为终端用户，我对小智说"声音小一点""暂停播放""十分钟后提醒我"，技能被正确识别并执行。
5. 作为管理员，当我修改了技能名（即训练标签），系统应明确提示"需要重新训练模型"并引导我提交训练，以免旧模型标签失效导致识别异常。
6. 作为管理员，我想在 IoT 分组下看到占位说明（tuya 集成规划中），以便理解该分组当前不可用而非系统缺陷。

## 4. 需求池

### P0（必须）

- **P0-1 概念统一（数据模型）**：技能数据模型新增 `domain` 字段（device/server/iot），服务端校验域合法性；术语层面废弃"command / mcp 技能 / intent"的对外称谓，统一称"技能"。
- **P0-2 默认技能目录按域重组**：`nlu/defaults.json` 中 11 个 reminder_* 全部标记 domain=server；command 词表合并为技能 `end_session`（domain=device，动作 kind=end_session，保留名不改动），词表文件退化为该技能的训练样本来源。
- **P0-3 管理台按域分组展示**：技能列表按域分组（设备/服务器/IoT），支持域筛选与技能搜索；编辑/保存/训练流程不变。
- **P0-4 训练影响应对**：技能改名 = 训练标签变更，管理台保存改名技能时必须强提示"旧模型标签失效，需重新训练"，并阻止未重训即发布（沿用现有"保存→提交训练"链路，本次不新做机制，仅补提示）。

### P1（应该）

- **P1-1 设备域示例技能落地**：提供开箱即用的设备控制技能样例——音量调大/调小/静音（mcp:self.audio_speaker.set_volume）、播放/暂停/循环（设备播放器工具，以 discovery 实际上报名为准），执行时校验设备已声明对应工具，未声明则拒并给可理解回话。
- **P1-2 技能归域可编辑**：管理员可修改技能所属域；改动仅影响分组展示与文档，不影响训练标签。
- **P1-3 统一目录文档**：在 docs 中输出 effective_catalog 说明，标注每个默认技能的域、动作、工具依赖。

### P2（可以有）

- **P2-1 IoT 域占位规划**：管理台 IoT 分组展示"规划中"说明页；数据模型为 tuya 设备/工具映射预留字段（不实现连接）。
- **P2-2 技能别名兼容**：为改名技能保留旧名别名（训练标签除外），旧引用/日志可读。

## 5. 待确认问题

- **Q1 域划分口径**：按"执行者"分域（默认方案）还是按"用户感知目标"分域？若按后者，音乐播放/暂停归服务器域（服务端 NLU 发起）。请裁决——它决定 reminder 与音乐控制的分组呈现。
- **Q2 "重启"归属**：设备重启是固件 MCP 工具（→ 设备域），但用户原话把它与音量并列在设备控制里，请确认是否需要服务端侧的设备管理动作（重启设备管理通道）。
- **Q3 tuya IoT 域**：本次是否只做分组占位与模型预留、完全不做集成？（默认：是）
- **Q4 旧技能名兼容**：改名后的旧技能名是否保留别名（P2-2）？是否允许直接删除？
- **Q5 工具名多板型差异**：音量/播放器工具名因板而异，默认目录中的设备域技能如何在非目标板型上提示"不支持"？（建议：执行校验时给固定话术，产品只要求不报错崩会话）
- **Q6 end_session 训练样本**：command 词表合并后，退场关键词的增删是否仍走独立词表文件，还是完全改为管理台编辑该技能例句？
